## 2. Core Architectural Separation: The Analyzer Contract

A core architectural invariant of CodeSentinel is the strict decoupling of the analysis engine from the backend web service:

```
┌─────────────────────────────────────────────────────────────┐
│                      analyzer/ Package                      │
│  (Zero FastAPI, Celery, Redis, SQLAlchemy, or HTTP imports) │
├───────────────┬───────────────┬──────────────┬──────────────┤
│  Ingestion &  │  Language &   │     AST      │  Dependency  │
│   Discovery   │   Framework   │   Parsers    │ Graph Engine │
├───────────────┴───────────────┴──────────────┴──────────────┤
│    Deterministic & Heuristic Rules (Security & Architecture)│
├─────────────────────────────────────────────────────────────┤
│        AnalysisPipeline -> Emits Structured AnalysisResult  │
└──────────────────────────────┬──────────────────────────────┘
                               │ Structured Output
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                    backend/ Service                         │
│   FastAPI Endpoints ──► Orchestrator Service ──► Celery Task│
│        ▲                     │                     │        │
│        │                     ▼                     ▼        │
│    REST API             PostgreSQL 16           Redis 7     │
└─────────────────────────────────────────────────────────────┘
```

### Analyzer Invariants:
1. **No External Network Calls**: The analyzer never initiates outbound HTTP requests or LLM calls. LLM enrichment is managed by backend orchestration services after static findings are collected.
2. **No Persistent DB Dependencies**: Operates entirely in-memory using strongly typed Pydantic models.
3. **Deterministic Execution**: Given identical source code files, the analyzer produces identical findings, graph topology, and metric scores.

## 3. Finding Classification Architecture

To ensure audit defensibility and prevent ungrounded claims, findings are strictly partitioned into three categories:

### 3.1 Deterministic Evidence
- **Definition**: Syntactic or structural match where code patterns unambiguously meet the rule condition.
- **AST Examples**:
  - Python `subprocess.call(..., shell=True)` with non-literal arguments.
  - Flask `app.run(debug=True)` or Django `DEBUG = True` in production settings.
  - React `dangerouslySetInnerHTML={{ __html: ... }}`.
  - Direct calls to `eval()` or `new Function()`.
- **Confidence**: `HIGH` or `CRITICAL`.

### 3.2 Heuristic Evidence
- **Definition**: Pattern, semantic, or context-derived signals where true risk depends on broader application state.
- **Examples**:
  - Storage of high-entropy strings or potential JWT tokens in `localStorage`.
  - Raw string formatting used near DB cursor executions where parameterized queries are expected.
  - High fan-out modules indicating architectural coupling.
- **Confidence**: `LOW` to `MEDIUM`, requiring human or AI review.

### 3.3 AI-Assisted Assessment
- **Definition**: Output generated by an LLM that consumes deterministic or heuristic findings alongside bounded code context.
- **Role**:
  - Validates candidate findings and evaluates reachable exploitability.
  - Explains the architectural or security impact in plain developer language.
  - Proposes a minimal, unified diff remediation patch.
- **Non-Authority Rule**: An LLM can downgrade or confirm an existing finding, but it cannot invent a vulnerability that lacks static/heuristic evidence.

## 4. Pipeline Execution Lifecycle

Analysis proceeds through sequential, observable stages:

1. **Ingestion & Discovery**:
   - Traverse target directory.
   - Ignore files based on standard patterns (`.git`, `node_modules`, `venv`, `__pycache__`).
   - Collect file catalog with metadata (relative path, size, file extension).

2. **Language & Framework Detection**:
   - Detect project primary language and framework markers.
   - Select corresponding AST parser pipelines.

3. **AST Parsing & Symbol Extraction**:
   - Parse files into AST nodes.
   - Extract imports, exports, class declarations, and function signatures.

4. **Dependency Graph Construction**:
   - Construct directed graph $G = (V, E)$ where $V$ represents modules/files and $E$ represents import relationships.
   - Compute Tarjan's strongly connected components to locate cycles.
   - Calculate node in-degree (fan-in) and out-degree (fan-out).

5. **Rule Evaluation**:
   - **Security Rules**: Run deterministic AST visitors and regex checkers over source files.
   - **Architecture Rules**: Run graph analysis algorithms over the dependency graph.

6. **Aggregation**:
   - Consolidate all findings into a unified `AnalysisResult` schema.
   - Compute aggregate risk score and architecture health metrics.

7. **AI Context Extraction (Optional/Asynchronous)**:
   - For flagged candidate findings, package the target AST block, import context, and call graph context.
   - Execute LLM completion via provider abstraction (`OpenRouterProvider` or `OllamaProvider`).
   - Validate LLM JSON output against `AIFindingEnrichment` schema.

## 5. Security & Isolation Boundaries

- **Input Validation**: All repository uploads and file paths are sanitized to prevent directory traversal (`../`) attacks.
- **Execution Sandboxing**: Static analysis runs in a restricted subprocess or isolated container with read-only filesystem mounts. No user code is executed during AST analysis.
- **Token Scrubbing**: Before transmitting code context to external LLM providers, known secrets and API tokens identified by the static secret scanner are redacted.

## 6. Implementation Status & Phase Boundaries

### 6.1 Phase 1 (Foundation) — Complete
- Established decoupled repository layout (`analyzer/`, `backend/`, `frontend/`, `docs/`).
- Core data models (`findings.py`, `graph.py`, `results.py`) and abstract rule interfaces.
- FastAPI backend foundation with `/health` and `/api/v1/health` endpoints.
- React + TypeScript + Vite frontend foundation.

### 6.2 Phase 2 (Repository Analysis Engine) — Complete
- **Ingestion & Discovery**:
  - Treats repository directories as strictly untrusted input. Never executes code, package scripts, or shell commands.
  - Enforces configurable limits (`max_file_size_bytes` default 5MB, `max_files` default 50,000).
  - Evaluates default exclusions, `.gitignore`, and `.sentinelignore` patterns via `IgnoreEngine`.
- **Deterministic Language Detection**:
  - Classifies Python, JavaScript, TypeScript, and Unknown based on file extensions.
- **Evidence-Based Framework Detection**:
  - Detects Django, Flask, and React based on accumulated manifest and syntactic evidence with confidence scores representing evidence strength.
- **Parser Architecture & Normalization**:
  - **Python**: Native `ast` module extracting imports, function definitions, class definitions, and dynamic calls. Catches `SyntaxError` gracefully.
  - **JavaScript / TypeScript**: Tree-sitter provides concrete syntax trees suitable for structured parsing of JavaScript, JSX, TypeScript, and TSX. Extracts syntactic structure, imports, exports, symbols, and source locations. Does not claim complete semantic analysis.
  - **Normalized Representation**: Emits uniform `ParsedFile` objects containing imports, exports, symbols, and non-fatal error records.
- **Dependency Resolution**:
  - Distinguishes `LOCAL`, `STDLIB`, `EXTERNAL`, and `UNRESOLVED` dependencies.
  - Uses runtime `sys.stdlib_module_names` for Python standard library identification.
  - Uses an explicit maintained list of Node.js runtime built-ins.
  - Resolves local imports (`./`, `../`, extensions, and index files).
  - Unresolved imports are explicitly marked as `UNRESOLVED` and never silently discarded.
- **Architecture Graph & Metrics**:
  - Constructs directed graph using NetworkX (`DiGraph`).
  - Computes `fan_in`, `fan_out`, coupling density, and detects circular dependency cycles.
  - God-module classification and architectural smells are intentionally deferred to the Phase 3 rule engine.
- **Resilience**:
  - Malformed files are captured into `parsing_errors` without aborting the pipeline run.

### 6.3 Known Parser & Resolution Limitations (Phase 2)
- Complex TypeScript path mapping (`tsconfig.json` `paths` aliases) and monorepo workspace package aliases are not yet fully resolved in Phase 2; such imports are recorded as `EXTERNAL` or `UNRESOLVED`.
- Dynamic runtime imports with computed string expressions (e.g. `import(computePath())`) cannot be statically resolved to concrete files.
